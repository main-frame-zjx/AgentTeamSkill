# AT_team_discuss

`meeting-context` 在会前同步全员工作记忆。若返回 `pending_memory`，用 `memory-read` 同时查看实时事实和手改差异。未定事项保留在纪要中。

有行动项时确定其目标版本。行动项可各自传 `version`，否则采用会议的 `version` 或项目已登记的 `current_version`。默认版本已发布时，向用户确认新迭代并调用 `set-iteration`。重试使用原会议输入。

1. 只从含 AT.json 的当前目录开会，`meeting-context` 的 `--root` 取实际当前目录。确认当前推理级别为 Ultra。若运行时不能可靠提供该信息，请用户确认已选 Ultra；非 Ultra 时提示切换。至少需要主持人与另一位注册角色，以及可用的子 Agent 工具。
2. 缺主题时通过可用的输入框向用户征集主题；无输入框时用聊天。主持人默认“项目负责人”，可由用户指定；默认角色不存在时请用户从已登记角色选定。调用 `meeting-context` 获取全员名单及档案路径。
3. 主线程读取主持人的 Agent.md，并用 `memory-read` 取得交接记录，先向用户作主持人开场，明确会议目标、需要作出的决定。**为每位其他角色启动一个独立子 Agent**，给它会议主题、开场、该角色的 Agent.md 和 `memory-read` 交接记录，以及明确的角色职责，要求先阅读这两份材料。保留角色与 agent 的对应关系。子 Agent 负责发言和磋商，由主持人统一写纪要与需求。
4. 主持人开场后，至少进行 10 轮全员讨论。第一轮每个角色独立陈述，主持人也给出意见。此后每轮由主持人把上一轮的意见、分歧和跨角色依赖反馈给各角色，全员回应并逐步细化决议。每轮收齐主持人和所有其他角色的实际发言才计为一轮。完成第 10 轮后，仍有待议问题时可以继续。可用并发低于角色数时在平台支持的范围内分批调度，保留每个角色的独立上下文；如果平台无法覆盖全员，说明缺少的席位，暂缓形成完整决议。不可代写缺席角色发言。
5. 遇重大玩法、范围、资源或目标取舍时，以具体选项、影响和角色意见征求用户裁决，收到回答再推进相关议题。未决事项单列。向用户呈现议定事项、负责人和可检查的验收条件。
6. 由主持人一次调用 `meeting`，它内部调用 `$at-add-worklist` 相同的建单程序，并返回纪要路径及任务编号对照。纪要通常位于 `public/meetings/`；团队仓库占用该名称时位于 `public/meeting-notes/`。详细输入见共用接口的会议示例。使用稳定会议编号和行动项 key，重试沿用原始输入。已议定行动项直接创建，会议可以没有行动项。主持人把实际纪要路径和已定决议发给仍在会的受影响角色，要求各自调用 `$at-manage-memory`，用 `memory-patch` 将本角色的决定和依赖写入交接记录。主持人处理自己的交接记录；子 Agent 已结束时，主持人按已确认的决议逐角色读记忆并提交补丁。收齐写入结果或无需变更的理由，再汇报纪要和分派编号。

首次给尚未登记需求前缀的角色分派时，在行动项中提供该角色的 `prefix`。使用简明中文标题，或用 `summary` 单独概括文件名。纪要中沿用稳定需求编号。

共用入口位于本技能目录的 `../at-init-team/scripts/at.py`。 将它解析为绝对路径后，从用户的项目上下文运行 `python -X utf8 "<入口>" <命令> --root "<项目目录>" --input "<UTF-8 JSON文件>"`。只读空输入可省略 `--input`。[命令接口](../at-init-team/references/commands.md) 给出了字段和重试约定。
