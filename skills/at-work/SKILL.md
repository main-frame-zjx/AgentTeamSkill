# AT_work

## 一、确认角色，收齐本轮待办

在角色目录使用当前角色，项目根有多个候选时先选定身份。运行只读 `work-context` 取得角色档案、交接记忆、个人技能、自有需求、待我验收、漏发提醒和工作树状态。同一会话且上下文完整时可传上次的 `agent_sha256` 与 `memory_sha256`，每次仍要刷新动态任务，核对 `manual_diff`。按需读取匹配的个人技能。

调用 `$at-receive-message` 收齐本轮所有未处理消息。记录缺损数据的告警，把仍有效的漏发事件列入清单。

## 二、动手前列编号清单

按稳定需求 ID 合并收件、自有需求、待我验收和漏发提醒，保留每个消息 ID；专题协作单列。每项写明优先级、行动、完成条件，遵守用户指定范围。收件标记沿用 P0 打回、P1 送验、P2 审阅反馈与协作、P3 关键同步。执行时优先返工和解除阻塞他人的验收、协作，再推进自有需求。自有需求通常列为 P2。清单末尾固定列出 P3 通讯结算、记忆更新和终检。[清单与补发](references/checklist-and-comms.md)

## 三、逐项执行，留下证据

- 指定自己验收时调用 `$at-review-work`，在本轮收尾统一结算消息。对照当前有效验收人与条件。验收改派后，原验收人核实自己已完成交接，可用 `noted` 记录改派和实际去向。自验需求直接列入清单。验收人为用户时，等待本人给出结论。
- 自有需求按指定路径或 ID 用 `show` 核对角色、阶段和依赖，优先续做处理中任务，再领取可执行新需求。阅读有效条件和历史，用 `library-index` 检索知识库，跨角色可传 `scope: project`，用 `library-read` 核对依据。调用 `$at-manage-workspace` 开始任务。
- 修改团队代码前检查角色工作树与脏文件来源，尽早同步远程 main。在角色分支提交相关文件，经 `sync` 后针对实际提交自测，再用 `deliver` 推送。阶段成果归入角色的 `report/`，离线 HTML 使用 `publish`，其他格式使用 `report-dir`。管理角色通过 `$at-publish` 交付版本程序包、用户指南或迭代中的甲方总览。[交付与报告细则](references/delivery.md)
- 送验前逐条对照需求当前有效的 `criteria` 自检，将对应测试结果、提交 SHA、交付物相对路径写入 `evidence`，调用 `$at-manage-workspace` 移至待验收。有可供人类初学者学习的完整设计或可复用方案时，用稳定的候选 key 登记 `candidates`。每项完成后记录结果与证据；受阻时用需求 `note` 记下缺少的输入与恢复位置，原收件保留 pending。

## 四、结算、更新记忆、对照终检

重新读取本轮相关需求的有效流转事件与已发消息。调用 `$at-reply-message` 核销本轮已完成收件并发送必要提醒。将本轮新流转与仍有效的漏发合并到一次结算，核对回执；等待澄清的事项以 `deferred` 记录阻塞并保留待办。收尾调用 `$at-manage-memory` 更新交接现场。对照开工清单逐项列明已完成、受阻或本轮跳过，核对证据、回执、剩余待办与交付入口。

通讯优先使用 `agent-team-chat` MCP，传入会话绝对目录 `working_dir`。未挂载时使用[通讯 CLI](../at-receive-message/references/protocol.md)。需求及工作树使用 `../at-init-team/scripts/at.py`，解析为绝对路径后从项目上下文运行。[命令接口](../at-init-team/references/commands.md)
