# AT_add_worklist

每条新需求都绑定目标版本。用户未指定版本时，从实际调用目录逐级向上找到最近的 `AT.json`，自动使用其中的 `current_version`。用户给整批需求指定版本时传顶层 `version`，有单项例外时在该项内传 `version`。单项优先于批次，批次优先于项目当前版本。若需继承的项目版本缺失或已发布，请用户指定新迭代，用 `set-iteration` 登记后继续。重试旧请求时沿用原始输入和已绑定版本。

1. 确定每项需求的一个负责人，从 `project` 返回的注册角色中选择。将目标拆到可独立交付的粒度，写清可观察的验收结果。默认验收人为“项目负责人”，用户可指定其他注册角色或“用户”。跨角色协作时可分别建单，在目标或来源中写清依赖与交接。
2. 给每项分配稳定的 `key`。有外部编号时沿用来源编号；临时口述需求用新 UUID，并在首次调用前保留本次输入，以便重试。同一项目内 key 唯一。会议由主持人的 `meeting` 命令将会议编号与行动项 key 组合，调用本技能共用的建单程序，无需二次创建。
3. 用 `AT-<角色前缀><五位流水号>-<中文概括>.md` 命名。先读取该成员在 AT.json 中的 `task_prefix`。首次建单时通过 `prefix` 提供项目内唯一的英文前缀，例如策划用 Design、工程师用 Dev、美术用 Art、项目负责人用 PM；程序会登记并复用。用能看出交付内容的中文短标题；原标题较长或为外文时，另传 40 字以内的中文 `summary`。流水号由脚本按角色跨四个状态目录分配。
4. 调用 `add-tasks`。下面的需求省略了版本。如果项目当前是 `v1.0`，脚本会将 `"version":"v1.0"` 写入需求正文。若这是该角色的第一条需求，文件名为 `AT-Dev00001-坦克撞墙停止.md`。
```json
{"items":[{"key":"design-01/collision","role":"高级工程师","prefix":"Dev","title":"坦克撞墙停止","goal":"玩家坦克移动时保持在围墙以外。","criteria":["四个方向正面撞墙都停止","贴墙转向后能沿墙移动"],"source":"首轮玩法设计"}]}
```
5. 根据命令结果列出每条需求的稳定编号、角色、实际绑定的目标版本和可点击的文件路径。相同 key、相同需求内容重试会返回原文件。开始、退回和归档均保留文件名；会议纪要继续使用正文内的稳定编号。已有需求的补充或修改请使用 `$at-manage-workspace`。

共用入口位于本技能目录的 `../at-init-team/scripts/at.py`。将它解析为绝对路径后，从用户的项目上下文运行 `python -X utf8 "<入口>" <命令> --root "<实际调用目录>" --input "<UTF-8 JSON文件>"`。只读空输入可省略 `--input`。[命令接口](../at-init-team/references/commands.md) 给出了字段和重试约定。
